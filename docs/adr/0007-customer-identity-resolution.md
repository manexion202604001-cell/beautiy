# ADR 0007: 顧客ID解決（名寄せ）は強い一意性のみ自動、統合は手動 + Undo

- 状態: 承認（Accepted）
- 日付: 2026-10-01
- 関連: requirements.md 4章 / FR-01 / FR-03、`modules/customers/identity.ts` / `duplicates.ts` / `merge.ts`

## Context（背景）

- 顧客は LINE（LIFF）、Web 予約、OTP、外部予約媒体、スタッフ登録など複数の入口から作られ、同一人物が重複登録されやすい。
- 要件 4.1: 完全一致ルールと類似候補ルールを分離、自動マージは強い一意性がある場合に限定、マージ時は予約・カルテ・会計・口コミ・メッセージを正規 Customer ID へ再リンク、履歴を監査に残し可能な範囲で Undo。
- 誤統合は個人情報の取り違え（他人のカルテ・会計が見える）につながり、未統合よりも被害が大きい。
- 日本語の氏名はひらがな/カタカナ/全角半角/空白の揺れが大きい。

## Decision（決定）

1. **正規化**: 電話は E.164（`normalizePhone`）、メールは小文字、氏名・カナは NFKC + ひらがな→カタカナ + 空白除去 + 小文字（`normalizeKana` と DB 関数 `normalize_search_text` を同一規則に保つ）。
2. **取込時の自動紐付け（`resolveCustomer()`）** は次の順で、強い一意性がある場合のみ既存顧客に紐づける:
   1. `customer_identities` の `(provider, provider_account_id, external_id)` 一致（統合済みなら統合先へ）
   2. 正規化電話番号が一致する有効顧客が **ちょうど1件**
   3. メールが一致する有効顧客が **ちょうど1件**
   該当なし・複数該当は新規顧客を作成する。紐付け時は既存の空欄の連絡先のみ補完し、既存値は上書きしない。
3. **既存顧客同士の自動マージは行わない**。重複候補を提示し、`customer.merge` 権限者が確認して手動マージする。候補は完全一致（電話/メール、score 1.0）と類似（氏名一致+生年月日、またはカナ/氏名類似度 ≥ 0.85 かつ生年月日または電話下4桁一致）を分けて表示する。「重複ではない」判定は `customer_duplicate_dismissals` に保存。
4. **マージ** は両顧客を ID 順にロックし、17テーブルの `customer_id` を付け替え、タグは和集合、店舗関係は付け替え/終了、配信許可は拒否優先（AND）、空欄プロフィールを補完、ポイント・統計を再計算し、source を `merged`（`merged_into_id`）にする。移動行 ID と両者スナップショットを `customer_merge_logs` に保存し、監査 `customer.merge` とイベント `customer.merged` を発行。
5. **Undo** は、後続の関連マージがない場合に限り（逆順で取り消す）、記録した行のうち現在も target に属する行を戻し、補完項目・配信許可・タグ・関係を復元する。

## Consequences（結果）

**良い点**
- 誤統合のリスクを最小化しつつ、LINE / 電話 / メールの強い識別子では手間なく同一顧客に集約される。
- マージは完全に記録され、誤操作を Undo できる。配信拒否の意思は統合後も維持される（拒否優先）。

**悪い点・リスク**
- 電話番号を家族で共有している場合、取込時に家族の別人へ紐づく可能性がある（電話一致がちょうど1件の条件）。顧客詳細で連携元を確認・解除（`DELETE /customers/:id/identities/:identityId`）できるようにする。
- ゲスト予約の電話番号は未検証のため、なりすまし入力で既存顧客に予約が付き得る（顧客情報は応答しない）。Phase 2 で「OTP 検証済みのみ自動紐付け」への切替を Feature Flag で用意する（requirements 23.1）。
- Undo はマージ後に作られた行を target に残し、補完項目のマージ後編集は失われる。
- 重複候補の法人全体ペア抽出は自己結合のため、大規模法人では夜間バッチ化・候補テーブル化が必要になる可能性がある。

## Alternatives（検討した代替案）

| 案 | 不採用理由 |
|---|---|
| 類似度スコアによる自動マージ | 誤統合による個人情報取り違えのリスクが許容できない |
| 名寄せしない（重複のまま運用） | 来店履歴・LTV・配信が分断され、要件 4 / FR-10 を満たせない |
| マージを論理リンク（統合ビュー）だけで表現し行を移動しない | 全クエリが統合関係を考慮する必要があり複雑化。権限・RLS・集計の実装負担が大きい |
| Undo なし | 誤操作の回復手段がなく、要件 4.1「可能な範囲で Undo」を満たさない |
