# ADR 0009: AI は説明可能な予測と人間承認必須の下書きに限定する

- 状態: 承認（Accepted）
- 日付: 2026-10-01
- 関連: requirements.md 14章 / 10.12 / 19.1、`0011_analytics_ai.sql`（`customer_scores`, `ai_suggestions`）、`config.ts`（`ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL`）

## Context（背景）

- 0.1: 将来的に AI エージェント・自動 CRM・売上予測・離脱予測へ拡張可能なデータ基盤を作る。
- 19.1: 「AI による自動外部送信」は MVP から外す。
- 顧客へのメッセージ・口コミ返信は店舗の信用に直結し、誤送信（不適切な表現・事実誤認・個人情報の混入）の影響が大きい。
- 初期はデータ量が少なく、機械学習モデルの学習・評価が成立しにくい。スタッフが「なぜこの顧客が離脱リスクなのか」を理解できることが行動につながる。
- 個人情報（特に要配慮個人情報）を外部 AI 事業者へ送ることには、法令上・信頼上の配慮が必要。

## Decision（決定）

1. **予測は説明可能なヒューリスティックから始める**。離脱スコア（再来遅延比のロジスティック変換 + 補正）、次回来店予測（最終来店 + 周期）、予測LTV、売上予測（既予約 + 曜日別季節移動平均）を夜間ジョブで計算し、`customer_scores.features` と `model_version`（例 `heuristic-v1`）を保存する。画面には根拠（特徴量）を表示する。
2. **生成は下書きのみ**。メッセージ下書き・口コミ返信案・カルテ要約・次のアクションを `ai_suggestions`（`status='proposed'`）に保存する。採用/却下は `decided_by` / `decided_at` で記録し、**外部送信はスタッフが通常の業務 API（自分の権限）で行う**。AI モジュールから messaging / reviews の送信関数を呼ばない（コード上の依存を持たない）。
3. **プロバイダ抽象化**: `AiProvider.generate(kind, input)`。`ANTHROPIC_API_KEY` 設定時は Anthropic Messages API（`ANTHROPIC_MODEL`、既定 `claude-sonnet-5-5`）、未設定・障害・タイムアウト（30秒）時は決定的テンプレート（`provider='heuristic'`）にフォールバックする。
4. **PII 最小化**: プロンプトに氏名・連絡先・LINE ID・住所・生年月日・要配慮個人情報を含めない。顧客名等は `{{customer.name}}` のプレースホルダで生成し、送信時にテンプレート描画する。送信したプロンプト（マスキング後）は `ai_suggestions.input` に保存して監査可能にする。法人単位で生成AIを無効化できる（Feature Flag `ai.generative`）。
5. **権限**: `ai.use` に加え、対象リソースの閲覧権限（カルテ要約なら `karte.read`、離脱スコア一覧なら `customer.read`）を要求する。
6. **評価**: 予測は月次バックテスト（AUC・MAE・MAPE）、生成は採用率・編集量・却下理由・PII 混入検査で継続評価し、`model_version` 単位で比較・切替する。

## Consequences（結果）

**良い点**
- 誤送信リスクを構造的に排除（AI → 外部送信の経路が存在しない）。スタッフが内容に責任を持つ運用になる。
- API キーがなくても機能が動作し（テンプレート）、開発・テストが外部依存なしで完結する。
- 予測根拠が見えるため、スタッフが納得して行動でき、ルールの改善もしやすい。特徴量と版を保存しているため、将来の ML モデルへの置換・比較が可能。

**悪い点・リスク**
- 完全自動の CRM（AI が判断して自動配信）は実現しない。自動配信は従来のルールベース（`automations`）で行う。
- ヒューリスティックの精度には限界がある（14.6 の評価で改善判断）。
- 生成結果の品質はプロバイダ・モデルに依存し、モデル更新で出力が変わる → プロンプト版・モデル名を記録し回帰評価する。

## Alternatives（検討した代替案）

| 案 | 不採用理由 |
|---|---|
| AI による自動送信（承認なし） | 19.1 で MVP 除外。誤送信・炎上・個人情報混入のリスクが高い |
| 初期から機械学習モデル（学習基盤・特徴量ストア） | データ不足で精度検証が困難、運用負荷が高い。説明可能性も下がる |
| 顧客の全データを LLM に渡して要約・提案 | 個人情報・要配慮情報の外部送信となり、データ最小化原則に反する |
| 単一プロバイダへの直接依存（抽象化なし） | プロバイダ変更・障害時の代替・テストが困難 |
