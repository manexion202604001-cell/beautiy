# ADR 0010: ホットペッパービューティー / LiME とは予約通知メールで連動し、枠止めはスタッフ作業として管理する

- 状態: 承認（Accepted）
- 日付: 2026-10-01
- 関連: requirements.md FR-06 / 0.2、ADR 0008、architecture.md 6.4、operations.md 9.4、`modules/integrations/mail/*`、migration `0131_manual_slot_blocks.sql`

## Context（背景）

- 店舗は ホットペッパービューティー（SALON BOARD）と LiME で既に予約を受けており、Salon OS の台帳とリアルタイムで揃えたい（ダブルブッキング防止）。
- どちらも予約の取得・枠の更新を行う **公開 API を提供していない**。他社の「連動」製品は媒体運営会社との個別契約、または管理画面の自動操作（ログイン情報を預かるRPA・スクレイピング）で実現している。
- 要件 0.2 は「特定外部予約媒体の非公開 API への依存」を非目的とし、ADR 0008 は公式手段のみを使うと決めている。管理画面の自動操作は規約違反・アカウント停止・画面変更での停止のリスクがある。
- 一方、両媒体とも **予約の受付・変更・キャンセル時に店舗へ通知メールを送る**。メールは店舗が自由に転送できる。

## Decision（決定）

1. **取り込み（媒体 → Salon OS）は予約通知メール**で行う。連携アカウント（`hotpepper_mail` / `lime_mail`）ごとに推測困難なトークン付き受信URL `POST /v1/webhooks/inbound_email/:token` を発行し、店舗はメール受信サービス（SendGrid Inbound Parse / Mailgun Routes / Postmark Inbound / Cloudflare Email Routing など）経由で通知メールを転送する。JSON・`application/x-www-form-urlencoded`・`multipart/form-data` を受け付け、Mailgun は署名検証も任意で行う。
2. メールは既存の Webhook パイプライン（ADR 0008）で `webhook_events` に保存（event id = アカウント + Message-ID、なければ本文ハッシュ → 重複配信は無視）→ ジョブで解析 → 既存の同期エンジン `processExternalBooking` に流す。競合ポリシー・競合キュー・顧客名寄せ・`external_bookings` の追跡はAPI連携と同じ。
3. **解析はラベル方式**（`予約番号` `来店日時` `お客様名` `スタッフ` `メニュー` …、全角/半角を NFKC で正規化）。表記ゆれは連携設定 `config.mail.labels` で追加できる。スタッフ・メニューは「対応表 → 名前の自動一致（一意の場合のみ） → 既定メニュー」の順に解決し、解決できないものは `unknown_staff` / `unknown_menu` の競合として人が判断する。予約番号のないキャンセル通知は取り込み済み予約の日時で照合する。
4. **反映（Salon OS → 媒体）はスタッフ作業**とする。Adapter に `pushMode: 'manual'` を宣言すると、push エンジンは API を呼ばず `external_slot_blocks.manual = true` の依頼を `action_required`（枠を止める）/ `remove_required`（再開する）として収束的に管理し、通知メールを送る。スタッフが媒体の管理画面で操作して「対応済み」を押すと `pushed` / `removed` になる。予約の発生元の媒体には依頼を出さない（自分の予約で自分の枠を止めない）。
5. **既存予約はCSVで一括取り込み**（`POST /integrations/:id/import-csv`、ドライラン既定）。行ごとに別トランザクションで処理し、失敗行が他の行を巻き戻さない。
6. 解析結果は事前に確認できる（`POST /integrations/:id/parse-test`）。

## Consequences（結果）

**良い点**
- 規約・契約に抵触せず、媒体側の操作は店舗が普段行うもの（メール転送・枠止め）だけ。媒体の画面変更で止まらない。
- 媒体 → Salon OS は通知メールの到着から数秒〜数十秒で反映され、5分ごとのポーリングより速い。
- 同期エンジン・競合キュー・監査は既存のものを再利用し、ドメインロジックは不変。
- 公式APIが提供された・契約が取れた場合は、同じ provider 名で `pushMode: 'api'` の Adapter に差し替えるだけで自動の枠反映へ移行できる。

**悪い点・リスク**
- 媒体側の枠止めは人の作業なので、作業までの間はダブルブッキングの可能性が残る（依頼一覧・ダッシュボード表示・通知メールで最小化）。
- 通知メールの書式変更で読み取れなくなる可能性がある（ラベル追加で対応、読み取れない場合は日時なし → ジョブが恒久エラーで DLQ に残り、運用画面で再処理できる）。
- メールに含まれない情報（媒体側の詳細な顧客属性・クーポン内容）は取り込めない。

## Alternatives（検討した代替案）

| 案 | 不採用理由 |
|---|---|
| SALON BOARD / LiME の管理画面をRPA・スクレイピングで自動操作 | 要件 0.2・ADR 0008 に反する。規約違反とアカウント停止のリスク、ログイン情報の預かり、画面変更での停止 |
| 媒体の非公開API（アプリ通信の解析） | 同上 |
| 媒体運営会社とのパートナー契約によるAPI連携 | 最も望ましいが契約未確定（23.1）。契約が取れた時点で `pushMode: 'api'` の Adapter を追加する |
| メールをIMAPでポーリング | メールアカウントの資格情報を預かる必要があり、遅延も大きい。受信Webhookなら資格情報不要 |
