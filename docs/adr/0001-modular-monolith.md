# ADR 0001: モジュラーモノリスで開始する

- 状態: 承認（Accepted）
- 日付: 2026-10-01
- 関連: requirements.md 1.1 / 21、architecture.md 2章・10章

## Context（背景）

- 要件は「集客→予約→顧客→施術→カルテ→会計→口コミ→再来店」の一気通貫で、顧客・予約・会計が密に結びつく（予約から会計、会計から顧客統計・口コミ依頼・分析）。
- 要件 21 は「モジュラーモノリスから開始し、予約同期・メッセージ・分析など高負荷領域を必要に応じて分離」「DB をサービスごとに最初から分断しすぎない。顧客/予約/会計の整合性を優先」と定めている。
- 初期の開発体制は少人数（＋開発AI）で、19モジュール・約280エンドポイント・88テーブルを段階的に実装する。
- 二重予約防止・会計の採番・名寄せの再リンクなど、複数テーブルにまたがる強い整合性が必要な処理が多い。

## Decision（決定）

1. **単一のデプロイ単位（Node.js / Fastify）と単一の PostgreSQL** で構築する。API サーバ（`src/index.ts`）と Worker（`src/worker.ts`）は同一コードベース・同一イメージで、起動エントリだけが異なる。
2. ドメインは `src/modules/<name>/` に分割し（19モジュール）、各モジュールは Fastify プラグイン（ルート）+ `service.ts`（ドメインロジック）+ `schemas.ts`（zod）+ 任意の `api.ts`（公開契約）で構成する。
3. モジュール間連携は **サービス関数・公開契約・ドメインイベント** に限定し、他モジュールの所有テーブルへ直接書き込まない（例: 配信は `messaging/api.ts` の `queueMessage()`、決済は `payments/api.ts`）。
4. ジョブ・イベント購読・定期タスク・初期データ・Webhook プロバイダは各モジュールの `index.ts` から副作用登録し、API と Worker が同じ登録内容を持つ（`modules/index.ts`）。
5. 1リクエスト = 1トランザクション（`req.tx`）。モジュールをまたぐ処理も同一トランザクションで整合させる。

## Consequences（結果）

**良い点**
- 予約作成・会計確定・顧客統合などをローカルトランザクションで原子的に実行でき、分散トランザクションや補償処理が不要。
- デプロイ・監視・ローカル開発が単純（DB 1つ・プロセス2種）。統合テストを実 DB で高速に回せる。
- 公開契約とイベントで境界を保つため、後からワーカー/サービスとして切り出せる（architecture.md 10章: メッセージ → 同期 → 分析の順）。

**悪い点・リスク**
- 境界はコード規約に依存するため、レビューで「他モジュールのテーブルへの直接書き込み」「循環呼び出し」を防ぐ必要がある（将来は lint ルール / 依存グラフ検査を CI に追加）。
- 1つのモジュールの重い処理（一括配信・同期・集計）が他に影響し得る → ジョブキューの `queue` 列でワーカーを分離して緩和。
- 単一 DB のスケール上限 → 分析はリードレプリカ / DWH へ、大量追記テーブルはパーティション化で対処。

## Alternatives（検討した代替案）

| 案 | 不採用理由 |
|---|---|
| 最初からマイクロサービス（予約・顧客・会計・配信を別サービス・別 DB） | 予約↔会計↔顧客の整合性に分散トランザクション/Saga が必要になり、初期開発・運用コストが過大。要件 21 に反する |
| モノリス（モジュール境界なし） | 初期は速いが、高負荷領域の分離（要件 21）が困難になる |
| サーバーレス関数群 | 長時間ジョブ・DB 接続数・トランザクション境界の制御が難しく、Postgres ジョブキュー/RLS の前提と相性が悪い |
