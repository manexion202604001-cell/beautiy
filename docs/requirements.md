## 1. プロジェクト概要

### 1.1 背景
既存SaaS（LiME等）は美容師向けカルテ・予約・POS一元管理として完成度が高いが、以下の理由から自社オーダーメイド開発を行う。

- 月額課金・売上連動課金からの脱却（総売上に応じた変動課金モデルの排除）
- 自社業務フロー・自動化基盤（ワークフロー自動化ツール）との深い統合
- AI機能（カルテ自動要約、次回提案、口コミ自動返信等）による差別化
- データ所有権の完全自社化と、将来の横展開（美容室以外のサロン業態）の自由度確保

### 1.2 目的
サロン運営に必要な「顧客カルテ」「予約」「会計/POS」「顧客コミュニケーション」「分析」を単一システムで一気通貫管理し、紙カルテ・複数ツール併用による業務ロスをゼロにする。

### 1.3 対象業態
- 主対象：美容室・理容室（正社員 / 業務委託 / フリーランス / シェアサロン混在を想定）
- 拡張対象：トリミングサロン、ネイル、エステ等（カルテ項目のテンプレート差し替えで対応可能な設計とする）

### 1.4 成功指標（KPI）
| 指標 | 目標値 |
|---|---|
| カルテ記入時間 | 1件あたり3分以内（紙比▲70%） |
| 予約のダブルブッキング | 0件 |
| 無断キャンセル率 | リマインド導入で▲30% |
| レジ締め所要時間 | 10分以内 |
| 顧客情報検索時間 | 5秒以内 |

## 2. スコープ定義

### 2.1 スコープに含むもの
1. スタッフ向けアプリ（スマホファースト / Web管理画面）
2. 顧客向けWeb予約ページ（顧客専用ネイティブアプリはPhase 2）
3. カルテ・予約・会計・メッセージ・分析の全バックエンドAPI
4. 外部サービス連携（LINE / Google / 決済 / 外部予約サイト）
5. マルチテナント基盤（多店舗・シェアサロン対応）
6. AI補助機能

### 2.2 スコープに含まないもの
- UI/UXビジュアルデザイン（別途デザイン工程。本書は画面要件・情報構造のみ定義）
- ハードウェア調達（レシートプリンタ・決済端末は既製品を利用）
- 給与計算・勤怠管理（歩合集計データのCSV出力までを本システムの責務とする）
- ホットペッパービューティー公式API連携（公式APIが提供されないため、予約メール解析等の準連携で代替）

## 3. 利用者・ロール定義

| ロール | 説明 | 主な権限 |
|---|---|---|
| システム管理者 | 自社（運営側） | 全テナント管理、プラン設定、監査ログ閲覧 |
| オーナー | サロン経営者 | 店舗設定、全スタッフ・全カルテ閲覧/編集、レポート、権限付与 |
| 店長 | 店舗責任者 | 店舗内の全カルテ・予約・会計・レジ締め |
| スタイリスト | 施術スタッフ | 自分の予約・カルテの作成/編集、他スタッフカルテの閲覧（設定に依存） |
| アシスタント | 補助スタッフ | カルテ閲覧・メモ追記のみ（会計不可を設定可能） |
| フリーランス/業務委託 | シェアサロン利用者 | 自身の顧客・料金・受付時間を独立管理 |
| 顧客 | エンドユーザー | Web予約、予約変更/キャンセル、カウンセリングシート事前記入、カルテ閲覧（公開範囲内） |

### 3.1 カルテ所有権モデル（重要）
- カルテの所有権を「サロン所有」「スタイリスト個人所有」から店舗単位・スタッフ単位で設定可能とする
- スタッフ退職時：サロン所有カルテは店舗に残置、個人所有カルテは持ち出し可（オーナー設定で制御）
- 所有権変更は監査ログに必ず記録

## 5. 非機能要件

### 5.1 性能
- 主要画面（カルテ表示、カレンダー表示）の初期表示：2秒以内（4G回線）
- 顧客検索応答：1秒以内（顧客10,000件時）
- 同時接続：1店舗あたり20端末、システム全体500テナントを想定

### 5.2 可用性
- 稼働率目標：99.5%以上（営業時間帯 9:00–21:00 は計画停止禁止）
- 障害時：予約カレンダーの読み取り専用キャッシュ表示（オフライン閲覧フォールバック）

### 5.3 セキュリティ
- 通信：TLS 1.2以上必須
- 保存データ：DB暗号化（at rest）、写真ストレージは署名付きURL（有効期限付き）でのみ配信
- 認証：メール＋パスワード（パスワードポリシー強制）、多要素認証（オーナーは必須推奨）、セッション有効期限設定
- テナント分離：Row Level Securityによる論理分離を必須とし、全クエリでテナントIDを強制
- 監査ログ：個人情報の閲覧・エクスポート操作を1年以上保持
- 脆弱性対応：OWASP Top 10準拠、リリース前に脆弱性診断を実施

### 5.4 個人情報保護（法令対応）
- 個人情報保護法（APPI）準拠：利用目的の明示、第三者提供の同意管理
- 顧客からの開示・削除請求への対応機能（カルテの論理削除→30日後物理削除）
- プライバシーポリシー・利用規約の同意取得と版管理

### 5.5 バックアップ・データ保全
- DB：日次フルバックアップ＋ポイントインタイムリカバリ（7日以上）
- 写真：別リージョンへのレプリケーション
- テナント単位の全データエクスポート機能（解約時のデータ返却）

### 5.6 端末・ブラウザ
- スタッフ用：スマホファースト（iOS 16+ / Android 12+ のブラウザ、PWA対応。ネイティブアプリはPhase 2判断）
- 管理画面：Chrome / Safari / Edge 最新2バージョン
- 顧客用Web予約：レスポンシブ、LINE内ブラウザでの動作保証

### 5.7 運用・保守
- ログ集約と監視（エラー率・応答時間のアラート）
- 機能フラグによる段階リリース
- サポート：管理画面内のお問い合わせ導線、FAQ

## 6. データモデル（主要エンティティ）

```
Tenant（テナント/契約単位）
 └ Salon（店舗）1:N
     ├ Staff（スタッフ）… role, 受付時間, 個人料金設定
     ├ Resource（セット面・シャンプー台等の設備）
     ├ Menu / Product（メニュー・店販商品）
     └ Customer（顧客）… 所有権（salon | staff）, タグ, 警告フラグ
         ├ Karte（カルテ）1:N … 施術履歴
         │   ├ KarteRecipe（薬剤・レシピ明細）
         │   ├ KartePhoto（写真）
         │   └ KarteMemo（メモ、記入者ID付き）
         ├ CounselingSheet（回答）/ ConsentDoc（同意書PDF＋署名）
         ├ Reservation（予約）… status, 指名区分, 外部予約元
         ├ Payment（会計）… 明細（PaymentItem）, 支払方法（複数）, ポイント
         ├ Message（メッセージ履歴）… channel（LINE/app/mail）
         └ Point（ポイント残高・履歴）
 CashierClosing（レジ締め）… salon_id, 日付, 理論値/実査値/差異
 AuditLog（監査ログ）… actor, action, target, timestamp
```

制約・整合性の要点：
- Reservation：`(staff_id, 時間帯)` および `(resource_id, 時間帯)` の重複を排他制御
- Payment確定後の変更は打消し伝票方式（元データ不変、修正はマイナス伝票＋新伝票）
- Customer削除は論理削除。Karte/Paymentは会計法令上の保存要件があるため匿名化して保持

## 10. 受け入れ基準（抜粋）

1. 同一スタッフに対し2端末から同時刻の予約を投入した場合、片方が必ずエラーになること
2. 会計確定→レジ締め後の修正が、権限者以外は不可能で、実施時は監査ログに残ること
3. スタッフAの個人所有顧客が、設定によりスタッフBの画面に一切表示されないこと
4. 顧客10,000件・カルテ50,000件のテストデータで検索1秒以内・カルテ表示2秒以内
5. LINE経由の予約→自動でLINE友だち紐付け→前日リマインドが自動送信されること
6. テナントAのユーザーがAPIを直接叩いてもテナントBのデータへ一切アクセスできないこと（RLS検証）
7. カルテ写真のURLが期限切れ後にアクセス不能になること

## 11. リスク・検討事項

| リスク | 対応方針 |
|---|---|
| ホットペッパー等の外部予約サイトに公式APIがない | 予約通知メールのパース取込（n8n）＋手動登録の併用。完全自動化は保証しない |
| 決済端末の機種依存 | Phase 1は金額手入力＋支払方法記録のみ。端末連携はPhase 2で機種を1つに限定 |
| カルテデータ移行（紙/他社SaaS） | CSVテンプレートと移行代行手順書を用意。写真は移行対象外を原則とする |
| 美容師の現場ITリテラシー | 3タップ以内でカルテ到達、音声入力等の入力負荷削減を画面要件に必須化 |
| 個人所有カルテの持ち出しトラブル | 所有権ルールを利用規約に明文化、変更操作は双方通知 |
